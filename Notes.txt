		Thread 3 → Test C

Question. Why do we return a new ArrayList in getResults()?

This part is important:

	synchronized (executionResults) {
	    return new ArrayList<>(executionResults);
	}

We don't want callers to receive our actual internal list.
If we don't send a new one, somebody could do: ExecutionStore.getResults().clear();
and potentially destroy our stored execution data.

    │ copy
    ▼
Caller

The AI layer can read the results without owning the underlying collection.

Question. Explain the role of synchronized. I have never used it so I don't know about it how it works or why or when or where to use?

synchronized is an important Java concept because we're building a parallel test automation framework.

1. What problem are we solving? Why do we need synchronized?

Remember that our framework can run tests in parallel:

	Thread 1 → LoginTest
	Thread 2 → SearchTest
	Thread 3 → CheckoutTest
	Thread 4 → PaymentTest

All of those threads can potentially interact with the same ExecutionStore. For example: ExecutionStore.add(executionResult);
At the same time, another thread could be doing: ExecutionStore.getResults();
So we have multiple threads accessing the same object.

That's where synchronization becomes relevant.
---------------------------------------------------------------
2. What does synchronized mean?

At a very basic level:
	synchronized makes threads take turns when accessing a particular piece of shared code/state.

Think of a single-room office with one key.

              Office
                🔑
             /      \
        Thread 1   Thread 2

Only one thread can have the key at a time.

If Thread 1 has it:
		Thread 1 → 🔑 → enters
		Thread 2 → waits

When Thread 1 finishes:
		Thread 1 → leaves → 🔑
		         ↓
		    Thread 2 enters

That's roughly what synchronization does.
---------------------------------------------------------------
3. What exactly is being synchronized here?

Look at:
	synchronized (executionResults) {
	    return new ArrayList<>(executionResults);
	}

The object inside the parentheses: "executionResults" is called the lock object (or monitor).

We're effectively saying:
"Before executing this block, acquire the lock associated with executionResults. If another thread already has that lock, wait."

So:
		Thread 1
		   ↓
		synchronized(executionResults)
		   ↓
		gets lock
		   ↓
		copies list
		   ↓
		releases lock

While simultaneously:

		Thread 2
		   ↓
		synchronized(executionResults)
		   ↓
		waits...
		   ↓
		Thread 1 releases lock
		   ↓
		gets lock
		   ↓
		copies list
---------------------------------------------------------------
4. Why do we need it specifically for getResults()?

Below line is reading the list while copying it.
	return new ArrayList<>(executionResults);

Imagine the list contains:
	[LoginResult, SearchResult, CheckoutResult]

At the exact same time, another thread does:
	executionResults.add(PaymentResult);

Now one thread is iterating/copying the list while another thread is modifying it. That's unsafe.

Conceptually:

Thread 1                         Thread 2

copy executionResults            add PaymentResult
       │                              │
       ├── LoginResult                │
       ├── SearchResult               │
       │                              ▼
       │                         modifies list
       ▼
  inconsistent view

Synchronization prevents that simultaneous access to the protected operation.
---------------------------------------------------------------
5. What happens if we remove synchronized?

We could write:
	public static List<ExecutionResult> getResults() {
	    return new ArrayList<>(executionResults);
	}

It might work most of the time.

But our tests might run:

	Run 1 → works
	Run 2 → works
	Run 3 → works
	...
	Run 99 → works
	Run 100 → weird failure

Because the problem depends on timing.
Thread 1 might be copying at exactly the same moment Thread 2 modifies the list.

These bugs are often called race conditions. 
(A race condition happens when the result depends on the unpredictable timing/order of multiple threads accessing shared data.)

Our add() is:

   ↓                                ↓
add result                         WAIT

release 🔓
                                    ↓
                             	 acquire 🔒
                                    ↓
                              	copy list
                                    ↓
                              	release 🔓

That's the coordination.

Question. Explanation on using structure interface based creating objects via classes implementing the interface
"AIClient aiClient = new GeminiAIClient();"

Think of your Selenium example -
	
	When you write: WebDriver driver = new ChromeDriver();

you're essentially saying: "I need a driver capable of performing WebDriver operations. Today I'm using Chrome."

If tomorrow you want Firefox:
	WebDriver driver = new FirefoxDriver();

Your test code can remain:

	driver.get(url);
	driver.findElement(...);
	driver.quit();

It doesn't need to become: FirefoxDriver driver = ... everywhere.
This is one of the biggest benefits of interfaces.
-------------------------------------------------------
Now, our framework has:

	public interface AIClient {
	    String generate(String prompt);
	}

Implementations:

             AIClient
            /        \
           /          \
GeminiAIClient     OpenAIClient

Our analyzer:

public class GeminiFailureAnalyzer {

    private AIClient aiClient;

    public GeminiFailureAnalyzer(AIClient aiClient) {
        this.aiClient = aiClient;
    }

    public FailureAnalysis analyze(ExecutionResult result) {
        String response = aiClient.generate(...);
        ...
    }
}

Now the analyzer isn't tightly coupled to Gemini.

We can inject: new GeminiAIClient() or new OpenAIClient() or even new MockAIClient()
And the analyzer doesn't care.

That's polymorphism + abstraction + dependency injection working together.
-------------------------------------------------------
1. Abstraction — "What do I need?"

	First, you define an interface:
	
		public interface AIClient {
		    String generate(String prompt);
		}
	
	This says: Any AI client must provide a generate() method.
	It does not say how generate() works.
	
	For example:
	
	public class GeminiAIClient implements AIClient {
	
	    @Override
	    public String generate(String prompt) {
	        // Call Gemini API
	    }
	}
	
	And perhaps:
	
	public class OpenAIClient implements AIClient {
	
	    @Override
	    public String generate(String prompt) {
	        // Call OpenAI API
	    }
	}
	
	The interface is the abstraction.
	So abstraction is basically: Expose what something can do, hide how it does it.

2. Polymorphism — "Which implementation will actually run?"

	Now look at: AIClient aiClient = new GeminiAIClient();
	The variable is an AIClient, but the actual object is a GeminiAIClient.
	
	That's where polymorphism comes in.
	
	Suppose:
		AIClient aiClient = new GeminiAIClient();
		String response = aiClient.generate(prompt);
	
	Java sees:
	
		aiClient
		   ↓
		actual object
		   ↓
		GeminiAIClient
		   ↓
		generate()
	
	So Gemini's implementation runs.
	
	But we could do:
		AIClient aiClient = new OpenAIClient();
	and:
		aiClient.generate(prompt);
	would now execute OpenAI's implementation.
	
	The calling code hasn't changed.
	That's polymorphism:
	The same interface/method call can behave differently depending on the actual object behind the reference.

3. Dependency Injection — "Who gives me the object?"

	Instead of doing this inside it:
	
		public class GeminiFailureAnalyzer {
		
		    *private AIClient aiClient = new GeminiAIClient();
		
		    public FailureAnalysis analyze(ExecutionResult result) {
		        String response = aiClient.generate(...);
		        ...
		    }
		}
	
	we do:
	
		public class GeminiFailureAnalyzer {
		
		    private AIClient aiClient;
		
		    *public GeminiFailureAnalyzer(AIClient aiClient) {
		        this.aiClient = aiClient;
		    }
		
		    public FailureAnalysis analyze(ExecutionResult result) {
		        String response = aiClient.generate(...);
		        ...
		    }
		}
	
	Now GeminiFailureAnalyzer says: "I need an AIClient. I don't care which one. Give me one."
	
	Then somewhere else:
		AIClient aiClient = new GeminiAIClient();
		GeminiFailureAnalyzer analyzer = new GeminiFailureAnalyzer(aiClient);
	
	We injected the dependency.
	
	The dependency is: AIClient
	And we're injecting: GeminiAIClient through the constructor.
	
	That's constructor dependency injection.

Question. When is onStart(ITestContext) and onFinish(ITestContext) called? How many times?

For an ITestListener, onStart(ITestContext) and onFinish(ITestContext) are called once for each TestNG <test> context, 
not necessarily once for the entire XML suite.

So if your testng.xml has:

	<suite name="Regression Suite">
	
	    <test name="Chrome Tests">
	        ...
	    </test>
	
	    <test name="Firefox Tests">

	    </test>

you can get:

	Chrome Tests
	    ↓
	onStart(Chrome Tests)
	    ↓
	test executions
	    ↓
	onFinish(Chrome Tests)
	
	Firefox Tests
	    ↓
	onStart(Firefox Tests)
	    ↓
	test executions
	    ↓
	onFinish(Firefox Tests)

Sequential:

Question. A problem faced during making is framework.

Reporting kinda was a challenge as we have analysis done in TestListener's method onFinish(ITestContext).
ThreadLocal<ExtentTest> is excellent while a test is running, because we know the current thread. 
But onFinish() is working with a collection of test results, 
so there was a need to find a way to identify which Extent test belongs to which result.

As read above, the onStart(ITestContext) and onFinish(ITestContext) are called once for each TestNG <test> context.

Think of it like, During execution:
	
		Thread 1 ──→ ExtentTest A
		Thread 2 ──→ ExtentTest B
		Thread 3 ──→ ExtentTest C

But after execution we have:

		ExecutionResult A ──→ ?
		ExecutionResult B ──→ ?
		ExecutionResult C ──→ ?

We need to establish those ? mappings. 
We have an association problem: 
we have the ExecutionResult objects because we explicitly store them in ExecutionStore during the relevant phases of TestListener. 
However, for the ExtentTest objects, we haven't preserved a direct mapping between each ExtentTest and its corresponding ExecutionResult.

When we reach onFinish(), we have our collection of ExecutionResult objects.
The ExtentTest objects are still associated with their execution threads through ThreadLocal while the tests are running.
So, we don't have a direct ExecutionResult → ExtentTest mapping available to the reporting code.

However, onFinish() needs to work with ExecutionResult objects and 
cannot rely on the original execution threads as the ThreadLocal is still useful during test execution, but it is not sufficient for post-execution reporting.

============================================================================================
Question. What was the solution to the reporting mapping problem?

Because we wanted to establish:

	ExecutionResult A ──→ ExtentTest A
	ExecutionResult B ──→ ExtentTest B
	ExecutionResult C ──→ ExtentTest C

We decided to preserve a direct mapping between ExecutionResult and its corresponding ExtentTest.
The existing ExtentTestStore uses a ConcurrentHashMap: Map<ExecutionResult, ExtentTest>

This means that when an ExecutionResult is created from the corresponding ITestResult, 
we can associate that exact ExecutionResult object with the ExtentTest that was created for that test.

We do not use the test name as the key because the same test can execute multiple times with different configurations.
For example:

	loginTest → Chrome → QA
	loginTest → Firefox → QA

The test name loginTest alone would not uniquely identify those executions.

We also do not need to retain ITestResult in the reporting store. 
ITestResult is used by TestNG during the listener callbacks, 
and ExecutionDataCollector converts it into our framework-level ExecutionResult.
Therefore, after collection, our framework can use: ExecutionResult → ExtentTest, as the direct post-execution reporting association.

Question. In ExtentTestStore class, why are we using ConcurrentHashMap?

ExtentTestStore can be accessed from multiple test-execution threads because the framework supports parallel execution.

For example:

		Thread 1 → ExecutionResult A → ExtentTest A
		Thread 2 → ExecutionResult B → ExtentTest B
		Thread 3 → ExecutionResult C → ExtentTest C


A normal HashMap is not thread-safe, so concurrent `put()` and `get()` operations can lead to unsafe behavior.

ConcurrentHashMap is designed for concurrent access and allows multiple threads to safely read and update the mapping.
The important point is that `ConcurrentHashMap` is being used because our store is shared across parallel test threads 
— not simply because Extent uses threads.

So the metadata stays associated with the correct execution thread.

Question. In the FailureAnalysisFormatter class, why are we replacing tags like < with &lt;?

In the output we display in extent report for AI failure analysis, we want it to be treated it as text.
So if AI sends a text containing any elements like <button> or <input>, if we put them as is in the string format we are creating,
it might be treated as an element.

Our formatter contains things like:

		<b>Root Cause:</b><br>

Now suppose Gemini returns: Root cause: <button> element was not enabled

Without escaping, Extent's HTML renderer sees:

		<b>Root Cause:</b><br>
		Root cause: <button> element was not enabled

and may interpret <button> as an actual HTML element.

With escaping:

		<b>Root Cause:</b><br>
		Root cause: &lt;button&gt; element was not enabled

the browser/Extent renderer displays:

	Root cause: <button> element was not enabled

But how does browser/Extent renderer displays: <button> and not: &lt;button&gt;
When Extent renders that as HTML, &lt; is interpreted as the HTML entity for <, so the displayed report shows <button

Question. How do we group/recognize that the retry attempts belong to same testcase?

We have introduced a new variable in ExecutionDataCollector called invocationId which is nothing but a combination of 
		"testClass + "#" + testName + "#" + parameters" 
		
Which will stay the same for 1 testcase even if it executes 3 times. So using this newly generated

Question. When we are creating summary in AISummaryGenerator class, why we throw 'IllegalStateException' exception?

We use IllegalStateException because the application received a response that it cannot use in its current state.
We are not saying the Java syntax is invalid. 
We are saying the AI-generated response does not meet the requirements for a usable execution summary.

One important distinction: this exception does not automatically mean Gemini itself threw an error. 
Our own code throws it after checking the response.

Question. Why introduce FakeAIClient class?

To debug framework-level issues without consuming Gemini API quota.
Failure Analysis uses the rule-based analyzer, while Execution Summary uses FakeAIClient during debugging.

Question. How do you switch the framework between AI mode and debugging mode?

Two changes are required:
	In config.properties and SuiteListener
	
For debugging mode: 
	 config.properties  = update ai.failure.analyzer configuration to RULE_BASED 
	 SuiteListener      = where we are creating object of AISummaryGenerator, put FakeAIClient()
	
For AI mode:
 	 config.properties  = update ai.failure.analyzer configuration to GEMINI 
	 SuiteListener      = where we are creating object of AISummaryGenerator, put GeminiAIClient()

Question. Why use suitelistener instead of testlistener?

Because AI analysis and execution summary are suite-level operations.
TestListener runs per TestNG <test> context, which can cause duplicate processing in a parallel suite. 
SuiteListener runs once after the entire suite, so it can process all ExecutionResults together.
